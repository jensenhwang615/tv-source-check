# 央视 + 广东 + 中国香港 + 体育 直播源（自动检测）

一份只含 **CCTV 全系列 + 广东地区 + 中国香港 + 体育** 的直播清单，配一条自动流水线：
从公开上游采集候选 → 实测能不能播 → 只把能播的写进 `dist/valid.m3u` → 每 6 小时重跑一次。

> 只做直播，不含点播。只检测，不生产。

## 当前实测结果（2026-10-20 19:00 晚高峰，佛山移动家宽）

>
> | 源 | `ratio` | 电视上的表现 |

> | 浙江广电 CCTV-13 | 92.9x | 秒开 |

## 两个总被问到的台

### CCTV-5+（18 号台）

**有。** 主线路 `124.165.251.82:85/tsfile/live/0019_1.m3u8`，实测 110ms 左右；
备线路 `223.78.65.165:9901/tsfile/live/0006_1.m3u8`，350ms 左右。

这两个编号是**截帧看过台标**确认的，不是照编号猜的——两台的编号规则完全不同
（同一套模板里，5+ 在 124.165 是 0019、在 223.78 是 0006），
而 CCTV-6 在 124.165 也确实是 0006。照编号类推一定错。

### 广东影视

**没有静态源可用，这是事实，不是没找。**

找过的路，全部失败：

| 途径 | 结果 |
|---|---|
| 各公开 IPTV 清单（9 个上游 ~580 条） | 只命中 1 条组播地址，无公网可用 |
| 广东电信老模板（`183.63.15.42:9901/1007`） | 2021 年的地址，整机超时 |
| 惠州/深圳/肇庆等外地模板（`113.81.20.168`、`218.17.216.102` 等 7 台） | DNS 解析失败或超时 |
| 广东台老官方 CDN（`nclive.grtn.cn`、`glive.grtn.cn`） | 域名已废弃 |
| iptv-org 频道库（`GuangdongDramaMovieChannel`） | 有频道条目，**没有流地址** |
| 自动检测型源库（Guovin/iptv-api 广东分支，522 条） | 只有 6 个广东台，无广东影视 |

**官方流确实存在**，但用不了：

```
https://tcdn.itouchtv.cn/live/gdys.m3u8?t_token=<每次打开页面动态生成>
```

`tcdn.itouchtv.cn` 是广东台自家的 TCDN，`gdys` 就是广东影视。
问题在后面那个 `t_token`——**不带 token 一律 403**，
而且每次打开荔枝网（`gdtv.cn/tvChannelDetail/53`，53 就是广东影视的频道 ID）都会重新签发一个。

播放器拉 m3u8 是每 4 秒一次，token 过期就断流。所以**没法做成静态订阅地址**：
录进 m3u 里，能看几小时，然后变成 403，用户看到的就是"这个台坏了"。
做本地代理实时换 token 也不行——抓一次 token 要跑一遍浏览器，约 10 秒，跟不上 4 秒的节奏。

**能看的办法**（都不需要这个仓库）：

1. 浏览器直接开 https://www.gdtv.cn/tvChannelDetail/53 ，官方免费
2. 手机装「触电新闻」或「粤 TV」，广东台全频道免费直播
3. 家里如果是广东电信/移动/联通 IPTV 用户，组播地址是 `rtp://239.77.0.217:5146`
   （需要路由器支持 IGMP 代理，或自建 udpxy 转 HTTP）


## 清单长什么样

`dist/valid.m3u` 不是把能播的源原样堆在一起，而是整理过的：

```
#EXTINF:-1 tvg-chno="1" tvg-name="CCTV-1 综合" group-title="央视",CCTV-1 综合
#EXTINF:-1 tvg-chno="1" tvg-name="CCTV-1 综合 (线路2)" group-title="央视",CCTV-1 综合 (线路2)
#EXTINF:-1 tvg-chno="2" tvg-name="CCTV-2 财经" group-title="央视",CCTV-2 财经
```

五条规则：

1. **分组固定顺序**：央视 → 广东 → 香港 → 澳门 → 体育（国内 → 国际免费 → 足球第三方）
2. **组内按台序排**：CCTV-1 到 CCTV-17 → CCTV-5+ → 4K/8K → CGTN；地方台按「卫视 → 主频道 → 城市台」排
3. **同一个台只出现一次**，多条线路紧邻并标 `(线路2)` `(线路3)`
4. **台号是固定的，不是数出来的**：央视直接用频道号（CCTV-5 永远是 5 号台），广东从 101 起、香港从 201 起、体育从 301 起。某个台这一轮没测通，它的台号就空着，后面的台**不会往前顶**。

第 4 条是踩过坑改的。老版本按「有一条给一个号」顺序编号，结果 CCTV-4 或 CCTV-5 一旦没源，CCTV-6 就顶上 4 号位——播放器里看到的正是「3 号台是 CCTV-3，4 号台是 CCTV-6」。改成固定台号后，缺台表现为台号留洞，一眼就能看出缺的是哪一台，而不是整体错位。

5. **不收录**：付费频道（央视付费数字台、华丽翡翠台）、名字撞关键词的误采内容（电视剧《特种兵之火凤凰》、风景摄像头"翡翠湾"）、别的地区的台（台湾 TVBS）

想看整理前的原始名字，看 `dist/status.json`；想改排序规则或增删频道别名，改 `scripts/curate.py` 顶部的表就行。

## 检测到底测什么

不是「HTTP 200 就算活」——这类源最常见的坑就是返回 200 但给你一个"已失效"网页。

| 层级 | 检查 |
|---|---|
| 连通 | DNS、TCP、TLS、状态码，超时 8s |
| 内容 | 响应体是不是真的 `#EXTM3U`，还是伪装成流的 HTML |
| 主列表 | 解析 `#EXT-X-STREAM-INF`，按 BANDWIDTH 挑最高码率，读 `RESOLUTION` |
| **分片** | 往下钻一层，真去拉第一个 `.ts`/`.m4s`，拉不到就是假的 |
| 裸流 | 直接从连接读 64KB，能读到字节才算通 |

五档判定：

| 状态 | 含义 | 去处 |
|---|---|---|
| `OK` | 真的能播 | `valid.m3u` |
| `SUSPECT` | 能连但不正常（返回网页、分片拉不下来） | `dead.m3u` |
| `DEAD` | 连不上 / 4xx / 空响应 | `dead.m3u` |
| `BLOCKED` | **本机 IP 被该站限流**，不是源坏了 | `valid.m3u`（不算失效，不计入可用率） |
| `SKIP` | 组播地址（`rtp://`），云端测不了，不谎报 | 不写 |

### 检测之外还要测速：`bench_all.py`

`check.py` 只能回答「打不打得开」，回答不了「打开后卡不卡」。
这两件事差得很远 —— 74.91 那台 CCTV-2 一直是 `OK`，但你打开要看 2 秒缓冲 6 秒。

所以选源顺序是：**先用 `check.py` 筛掉打不开的，再用 `bench_all.py` 量带宽，最后才排序。**

```bash
# 把清单里每条源都测一遍，结果写 sources/local_rank.json
python scripts/bench_all.py \
  --playlist sources/streams.m3u sources/backup.m3u sources/hk.m3u sources/sports.m3u \
  --timeout 6 --segments 1 --probe-bytes 524288 --concurrency 5

# 中途断了就续跑，已测的不会重测
python scripts/bench_all.py --playlist ... --resume
```

三个设计上的取舍，都是踩过坑之后改的：

| 做法 | 为什么 |
|---|---|
| **按主机分组，组内串行** | 同一台机器并发会互抢带宽。曾经把 CCTV-5 测成 0.3x，串行复测是 1.1x，差 4 倍 |
| **每条只读前 512KB** | 分片常有 5~10MB，全读一遍要 17 分钟。前 512KB 足够算出真实吞吐 |
| **边测边写 `.tmp/bench.jsonl`** | 全量扫容易中途卡死。分段落盘 + `--resume`，断在哪就从哪接着来 |

**必须在晚上测。** 白天测出来 1.9x 的源，晚高峰会掉到 0.2x ——
这份清单是给你晚上看电视用的，那就在晚上量。


`BLOCKED` 这一档是被现实逼出来的：主干 CDN 会按 IP 限流，GitHub 机房 IP 尤其容易中。
用 `--blocked-host 74.91.26.218` 指定，从它上面失败的条目就不会被误判成死源、也不会被踢出订阅清单。

## 为什么「延迟低」的源反而更卡

这一节是这个仓库踩过最大的坑，值得单独讲。

一开始选源只看 `latency_ms`（握手要多久），于是选出一批握手 100ms 的源，
数字比原来的 1500ms 漂亮十倍。结果电视上更卡了。

原因：**握手快慢和能不能流畅播，是两件不相关的事。**

| 源 | 码率 | 实际吞吐 | 比值 | 电视上的表现 |
|---|---|---|---|---|
| 山西联通 IPTV 模板 `124.165.251.82` | 8900 kbps | 1791 kbps | **0.2×** | 看 2 秒，缓冲 8 秒 |
| 海外转发 VPS `74.91.26.218` | 2000 kbps | 2678 kbps | 1.3× | 能播，偶尔卡 |
| **央视官网 CDN** | 1600 kbps | 156782 kbps | **145×** | 秒开，随便拖 |

`124.165` 那台握手只要 100ms，但它把 8~9 Mbps 的高码率流塞进一条只有
1.5~1.8 Mbps 上行的公网暴露端口。带宽是码率的五分之一，必然周期性缓冲。

**判断标准应该是 `吞吐 ÷ 码率`，至少要大于 1.3 才不会卡。** 这个值我叫它 `ratio`。

于是有了 `scripts/bench.py`：

```bash
python scripts/bench.py --playlist dist/valid.m3u            # 测全部
python scripts/bench.py --match "CCTV" --write-rank          # 只测央视，并写排名
```

它按电视播放器的真实行为量三件事：**首分片首字节耗时**（约等于点开后的黑屏时长）、
**流本身的码率**、**连拉几个分片的下载速度**，然后算 `ratio`。

两个细节必须注意：

1. **同一主机必须串行测。** 并发去打同一台服务器会互相抢带宽，测出来的数字偏低好几倍
   —— 曾经把 CCTV-5 测成 0.3×，串行复测其实是 1.1×。脚本现在按主机分组，组内串行、组间并行。
2. **测速要在自己家宽上跑，不要看 GitHub 机房的结果。** 机房在境外，到国内 CDN 的
   路由和带宽都不具代表性。

跑出来的排名写进 `sources/local_rank.json`，`curate.py` 会读它来决定哪个源排前面。

## 央视官网源：带宽高一个数量级

上面那张表里最后一行是真正的解法。央视官网
[`tv.cctv.com/live/cctvN/`](https://tv.cctv.com/live/cctv1/) 是免费公开直播，
背后走金山云、网宿、腾讯云、百度云、火山这些大厂 CDN，单条实测 **20~270 Mbps**。

抓取方式：播放地址是播放器动态取回来的（先请求 `p.data.cctv.com` 埋点接口再拿 streamUrl），
静态爬 HTML 拿不到，只能用浏览器监听网络请求 —— 这就是 `scripts/sniff_m3u8.py`
（Edge headless + CDP）的用途。批量版是 `scripts/fetch_official.py`：

```bash
python scripts/fetch_official.py                    # 抓 1~17 台
python scripts/fetch_official.py --append           # 顺手测速选优，写进 sources/official.m3u
```

三个踩过的坑：

- **每个台分到的 CDN 域名不一样。** CCTV-1 在 `bdydns.com`、CCTV-2 在 `myqcloud.com`、
  CCTV-7 在 `wscdns.com`、CCTV-11 在 `volcfcdn.com`。所以不能写一套模板套全部，必须逐台抓。
- **播放页下方的「推荐频道」会让嗅探抓串台。** CCTV-9 和 CCTV-14 都曾抓到 CCTV-13 的地址。
  现在按频道号过滤（地址里必须真的含 `cctvN`）。
- **`/live/hls_cdrm/enc1/av1/` 那条路径是 AV1 编码**，带宽也很高，但绝大多数电视盒子
  和智能电视只解 H.264，播出来是黑屏。脚本已排除它。

结果：CCTV-1~15、17 抓到官网源，起播 10~170ms，`ratio` 26~286 倍。
CCTV-16 和 CCTV-5+ 官网没有 H.264 直播页。

### 但是：官网源解出来是灰屏，最后整条剔除了

带宽高等于能拉下来，不等于能解出来。这是踩到的第四个坑，也是我一开始误判的一条。

`ffmpeg` 一上来就报错：

```
$ ffmpeg -i "<官网 m3u8>" -t 18 -vf "fps=1/3" f%02d.png
[h264] top block unavailable for requested intra mode
[h264] error while decoding MB 2 0, bytestream 94668
```

一开始我以为是「软解兼容性问题，浏览器能播」。但把帧抽出来看就明白了 ——
**f01~f06 全是 480×270 的纯灰色块，只有顶部几条噪点**：

```bash
# 没有 ffmpeg 的话，这一句就能拿到一个自带的可执行文件（约 25MB）
python -m pip install imageio-ffmpeg
python -c "import imageio_ffmpeg;print(imageio_ffmpeg.get_ffmpeg_exe())"
```

| 抽帧 | 内容 |
|---|---|
| 第 3 秒 / 第 9 秒 / 第 12 秒 / 第 18 秒 | 全灰，无画面 |

换 ffmpeg 7.1 重测，结果一模一样，所以不是版本问题。再往下挖，发现容器层其实是干净的：

| 检查项 | 结果 |
|---|---|
| TS 包头加扰标志（byte[3]>>6） | 4026 个包全是 `0`，未加扰 |
| 清单里的 `#EXT-X-KEY` | 不存在 |
| PES 起始码 `00 00 01 E0` | 出现 100 次，正常 |

**所以不是标准 DRM，是 H.264 码流本身解不出画面。** 路径里的 `cdrm`（CDRM）
大概率就是央视自己做的一层载荷处理：容器不加密、密钥标签也不给，但 slice 数据
解出来是乱的，只有官网播放器能还原。

关键佐证是**对照组**：同一套 ffmpeg 命令、同一个 `-vf` 参数，去抽第三方源
（`124.165` 的 CCTV-1），画面正常出「CCTV 综合」的演播室镜头。所以不是我的
抽帧方法有问题，也不是这台机器的解码环境有问题。

录满 60 秒再看，画面仍是整片灰褐色加顶部噪点条 —— 不是「起播缺 IDR 帧、
等一会就好」的临时现象。

所以最终决策是**整条剔除，不是降级成备选**：

- 降级没用。用户点「线路 2」看到一片灰，会以为清单坏了，比卡顿更糟。
- `sources/official.m3u` 和 `scripts/fetch_official.py` 保留作研究留档，
  但 `check.yml` 不跑它，`curate.py` 里 `_is_official()` 命中就直接不收录。

### 回归原问题：为什么「现在的源没第一次快」

三个原因叠在一起，都是同一个错误的不同侧面 —— **用「握手多快」代替了「能不能看」**：

1. **上一版换错了源。** 为了压延迟，把央视主力从第三方源换成了
   `124.165.251.82:85` 这类 IPTV 模板 —— 握手 100ms 看着快，但实测上行只有
   1.5~1.8 Mbps，而分片码率是 8~10 Mbps，`ratio` 0.1~0.2，看 2 秒缓冲 8 秒。
   **`latency_ms` 只量了握手，跟电视上卡不卡完全无关。**
2. **`sources/local_rank.json` 一直没生成。** `curate.py` 写了读实测排名的逻辑，
   但文件不存在，于是所有源都退回 `latency_ms` 兜底排序 —— 等于第 1 条的错又犯一遍。
   现在这份排名已经补上并提交，本机实测数据固化在仓库里。
3. **74.91.26.218 这台机器本身也退化了。** 今晚 19 点实测，它上面央视全线掉到
   0.2~0.6x（CCTV-1 0.4x、CCTV-5 0.2x），CCTV-13/15/16 更是 m3u8 能通但分片 404
   ——`check.py` 判它 `OK`，实际打开是黑屏。第一次那个「快」的版本，既是同一台机器，
   也是同一个时间段之外测的。**它的落差主要来自晚高峰，不是源换了。**

> 顺带纠正一个曾经的错误结论：一度以为「74.91 把央视全下线了」，还把它写进了
> `_DEAD_HOSTS` 硬剔除名单。后来发现那是 **IDE 沙箱代理**造成的假象 —— 同一台机器
> 绕过代理直连，200 且内容是正常 m3u8。教训：**测源前先确认请求没走代理**，
> `check.py` 里 `session()` 现在固定 `trust_env = False`。

### 现在的选源逻辑：一级源优先，第三方兜底

`curate.py` 里 `_is_primary()` 按**域名归属**判断这条源是谁在发流，命中的打
`_PRIMARY_DISCOUNT = 0.05` 的折扣，排到第三方前面：

| 类别 | 判定依据 | 举例 |
|---|---|---|
| **一级源（优先）** | 电视台 / 广电 / 持牌播出平台自己的域名 | `cgtn.com`、`gztv.com`（广州台）、`hyrtv.cn`（河源台）、`pybtv.cn`（番禺台）、`sun0769.com`（东莞台）、`cztv.com`（浙江广电）、`bestv.cn`（百视通）、`fengshows.cn`（凤凰） |
| 第三方（兜底） | 其余全部 | IPTV 模板、海外小 VPS、转播节点 |

折扣是乘 0.05 而不是直接置 0，意思是**「优先」不等于「免检」**：一级源如果实测
比第三方慢 20 倍以上，照样会被顶掉。判死的（`_STARVED_HOSTS`、官网灰屏源）在打折
之前就已经丢进 9000 / 1e9 档，不参与优先。

顺带说明：一级源优先看的是**谁在发流**，不是**播什么**。浙江广电的 CDN 上转
CCTV-13，仍算一级源 —— 运维责任在浙江广电，比某个海外小 VPS 靠谱得多。

### 央视剩下的问题：源本身没了

浙江广电这套 CDN 是今晚翻出来的唯一高带宽央视源。通道号和台名的对应关系没有
元数据，是逐台抽帧看台标识别出来的：

| 通道 | 台 | 实测（19:00 晚高峰） |
|---|---|---|
| `channel16/1080p` | **CCTV-1 综合** | 码率 4017k / 吞吐 84265k / **21.0×** / 起播 48ms |
| `channel22/720p` | **CCTV-1 综合** | 码率 1576k / 吞吐 49544k / **20.2×** / 起播 94ms |
| `channel21/1080p` | **CCTV-13 新闻** | 码率 2138k / 吞吐 79245k / **33.8×** / 起播 32ms |
| `channel40/720p` | **CCTV-13 新闻** | **92.9×** —— 整份清单里最快的一条 |
| 其余 20 多个通道 | 浙江卫视、钱江、浙江经济生活、浙江新闻、浙江少儿、之江纪录、浙江国际 | 用不上 |

**这套 CDN 上只有 CCTV-1 和 CCTV-13 两台央视**，41~130 号通道也扫过了，其余全是
浙江本地台和重复台。

### CCTV-2~17 为什么凑不出好源

这是当前最大的短板，而且**不是排序能解决的**。今晚把所有能查到的候选都测了一遍：

| 试过的路子 | 结果 |
|---|---|
| 央视官网 `tv.cctv.com` | 解出来是灰屏（见上一节），整条剔除 |
| `74.91.26.218`（曾经的央视主力） | 全线 0.2~0.6x，晚高峰被榨干；CCTV-13/15/16 分片 404 |
| `124.165.251.82` / `gmxw.7766.org` | 0.2~0.7x（8 Mbps 码率配 1.7 Mbps 上行） |
| `192.151.150.154` | 10 个台，但共享带宽：19:00 测 0.2~0.7x，19:10 再测 0.2x |
| iptv-org 中国区（147 条） | 央视部分全部指向 `74.91`，没有新东西 |
| vbskycn/iptv、YueChan、Kimentanm（700+ 条） | 同上，央视源都是已知的那几台 |
| `101.35.240.114:88`（覆盖全 18 台的转播站） | 全 404，已废 |
| 北京/山东/江西移动的 `PLTV` 模板 | 全部超时或 0x（组播/地域限制） |

**结论：免费公开源里，央视只有 1、4、9、12、13、15 这 6 台能达标。**
CCTV-5（体育）目前最好的是 `124.165` 的 0.7x —— 能出画面，但看西甲欧冠会卡。

对这几台，**央视频 App 是唯一可靠解法**（免费、全频道、不卡）。清单里保留它们
是为了「不方便装 App 时凑合看」，不是让你拿它当主粮。

## 香港这一块，先把话说清楚

104 条候选，通过 8 条。但「能播」和「该不该当主源」是两件事，性质得分开看：

| 频道 | 通过的线路从哪来 | 实测 `ratio` | 性质 |
|---|---|---|---|
| 凤凰卫视中文 / 资讯 / 香港台 | `fengshows.cn`（凤凰官方域名）的 CDN | 未测出（DNS 解析挂住） | **官方源**，最可靠，三条全通 |
| 翡翠台 ×3 线路 | 两个第三方转播节点（其中一条 relay 的是 TVB 付费 OTT「myTV SUPER」） | 1.0x / 0.5x | 未授权，**卡** |
| 明珠台 ×2（1 条已死） | 同上 | 0.9x | 未授权，**卡** |
| TVB Plus | 同上 | 0.3x | 未授权，**卡** |

**注意翡翠台的 1.0x** —— 这不是「能用但慢」，是「随时会缓冲」。
它意味着带宽刚好等于码率，任何波动都会卡住。想顺畅看得靠正规渠道。

**官方渠道实测全部拿不到，这是硬事实——不是我没找到：**

| 官方源 | 结果 |
|---|---|
| HOY TV `hoytv-live-stream.hoy.tv` | 超时（内地不通） |
| 港台 RTHK `rthktv3x-live.akamaized.net` | **HTTP 403，地域封锁** |
| 翡翠台内地合法直播渠道 | **不存在** |

所以「翡翠台怎么稳定看」这个问题，技术上是无解的。合法路径只有两条：

- **myTV SUPER**——TVB 官方 OTT，要香港 IP + 订阅
- **埋堆堆**——TVB 官方内地 App，有剧集点播，**没有翡翠台直播**

我的建议：翡翠台当「能用就用」，别当主粮。它的节点寿命以天计，TVB 的维权力度也远强于央视。
未收录 `华丽翡翠台`（Golden Jade）——实测它其实通，但那是 TVB 的付费频道，性质与免费台不同。

## 四个必须知道的坑

**1. GitHub Actions 的机器不在国内。** runner 跑在 Azure 美国/欧洲机房，测大陆 CDN 会大量假失败,
延迟数字也没参考价值。**这个项目最该做的第一件事是把 runner 换成你自己的电脑**：
仓库 Settings → Actions → Runners → New self-hosted runner → 选 Windows 按提示装，
然后把 `.github/workflows/check.yml` 里 `runs-on: ubuntu-latest` 改成 `runs-on: self-hosted`。
家里那台常开的机器跑，结果才准。

在自己电脑上跑的时候，**先关掉代理 / 科学上网工具**。走代理时出口 IP 在境外，
国内 CDN 和香港源会成片返回 403，实测可用率被压到 12%；同一份源直连家宽是 39%。
这两个数字的差距全是代理造成的假失败——而电视端不会走代理，所以直连的数字才是真的。

**2. 转播节点会限流，而且限的是 IP。** 这是我自己踩到的：探测 `74.91.26.218` 时连发一百多个请求，
之后整个 IP 全部 404，连之前能播的台都不给了；等了十几分钟才恢复。
所以 `backup.m3u` 里那些地址**别用脚本批量刷**，正常看不会触发。
家用宽带 IP 一般是干净的新 IP，反而比机房 IP 更容易通过。

**3. 一个台只挂一台主机，等于没有这个台。** 真实案例：央视 1/2/3/7/8/10/11/13/14/17
曾经全部指向 `74.91.26.218:82`。那台一限流，整组央视就从清单里消失，
电视上看到的现象正是「CCTV-3 之后直接跳到 CCTV-6」。这台的病根是**一台机器扛 18 个台**，
带宽被摊薄到每个台只剩 0.2~0.6x。现在的做法是每台至少两条不同主机的线路，
而且主力尽量压到持牌机构的 CDN 上（CCTV-1/13 走浙江广电，实测 20~93x）。

**4. 单一源"时好时坏"是常态。** 直播源经常这会儿通、下会儿 503。
每 6 小时跑一次，只在 `valid.m3u` 里留下当时能播的，本身就是在自动纠错。

## 零维护的兜底方案

m3u 这套东西本质上是「别人家的服务器」，再自动也有天花板。真正不会死的只有官方渠道：
